# V0.1 Cognitive Fact Page

This page explains the frozen V0.1 VF nodes. Canonical machine semantics remain in the sibling `.vf.md` files; this page is the human drill-down layer.

## Root

### root-why

V0.1 was built around one empirical requirement: the final Galaxy Buds3 Pro render path should stay active instead of being repeatedly created and destroyed around silence. The same implementation also accumulated a hot-path latency laboratory so category and routing experiments could be compared without changing the basic destination lifecycle.

### root-what

The executable dispatches explicit diagnostic modes first. Otherwise, after acquiring the single-instance guard, it enters the daily Process Loopback relay. The daily and hot-latency paths intentionally reuse the same ring/provider primitives so experiments exercise the same user-mode relay behavior.

### root-outcome

The daily path remains one long-running console-owned route until shutdown or fatal failure. The hot diagnostic path performs a bounded measurement sequence and returns summaries. V0.1 has no independent application shell above either path.

## Relay session

### relay-session-why

The relay session owns the complete lifetime of one daily audio route. The destination is started first so the Buds AudioClient is already active before Process Loopback begins feeding captured system audio.

### relay-session-what

The session resolves one active destination, validates a 48 kHz Float32 stereo mix format, constructs the ring/provider/player/capture objects, starts the destination, arms relay activation, then starts capture. A one-second health observation loop remains inside this same route lifetime.

### relay-session-outcome

Ctrl+C moves the provider back to keepalive before capture is stopped, then stops the destination player. Because the entire product lifetime and route lifetime are the same process flow, endpoint loss, suspend/resume, or topology changes have no outer supervisor capable of replacing only the route generation.

## Buffer boundary

### buffer-boundary-why

Process Loopback production and destination rendering are independent callback domains. V0.1 places one SPSC ring between them and requires the destination callback to remain fully supplied even before relay activation and during missing data.

### buffer-boundary-what

Before activation, incoming packets are admitted only up to a startup hold limit. The render provider enters RELAY only when ring fill can satisfy the current destination request plus the target cushion; any excess is trimmed. During runtime, captured silent packets are represented as zero writes, and the destination buffer is always cleared to real zeros before available ring frames overwrite its prefix.

### buffer-boundary-outcome

The destination callback always returns its full requested byte count. The ring exposes underrun and overflow frame counters, but V0.1's overflow counter does not distinguish dropped audible PCM from dropped silent zero frames, which limits the product-level meaning of large overflow totals.

## Runtime health

### runtime-health-why

Early development logging was intentionally reduced so normal daily operation did not print status every second. Health filtering therefore focuses on conditions that accumulate or remain abnormal long enough to be worth surfacing.

### runtime-health-what

The filter tracks capture/render rates, underrun and overflow deltas, callback errors, sustained high fill, empty-ring while capture is active, and slow render. It converts those observations into sparse HealthEvent values.

### runtime-health-outcome

The daily runtime prints those events. Health is observational only: no event changes provider mode, resets the ring, recreates capture/render clients, or performs reconnect policy.

## Hot latency probe

### hot-probe-why

Category and routing experiments needed repeatable measurements after the destination path was already hot, rather than repeatedly measuring cold AudioClient startup behavior.

### hot-probe-what

A child process renders chirps to a sacrificial physical sink. The parent captures only that process tree through Process Loopback, relays it to the persistent Buds destination, and simultaneously records a microphone. QPC-tagged capture snapshots and chirp correlation are used to locate each signal in the two recorded paths.

### hot-probe-outcome

The tool reports SRC→LOOP, LOOP→MIC, and SRC→MIC intervals plus medians/min/max and ring diagnostics. Those numbers are useful for relative A/B work; the archive does not reinterpret them as a separately calibrated absolute acoustic latency.
