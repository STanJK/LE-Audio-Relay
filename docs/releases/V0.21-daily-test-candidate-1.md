# V0.21 Daily Test Candidate 1

**Status:** Frozen daily-use candidate — full validation in progress  
**Frozen:** 2026-09-27  
**Runtime implementation baseline:** `326fa42cf2a6069c97ab11c9a60e635b4481c1c0`  
**Branch:** `release/v0.21-daily-test`

## Purpose

This candidate freezes the first Round4 build intended to be left running as the user's normal daily audio route while evidence is collected for a later public release.

It is **not yet a stable release**.

The purpose of freezing it before testing completes is to preserve an exact evidence-bearing baseline. Bugs, regressions, and long-run observations can therefore be attributed to one immutable candidate instead of a moving development branch.

## Included baseline

```text
Tray / Supervisor
├── Endpoint lifecycle observer/probe
├── Power lifecycle observer
├── Lifecycle-only persistent journal
└── Disposable worker generation
    └── RouteSession
        ├── Process Loopback capture
        ├── PCM relay boundary
        │   └── ProvisionalPositiveDriftGuard
        └── Persistent Buds render
```

### Endpoint lifecycle

- Core Audio notifications are wake-up signals only.
- Fresh enumeration is authoritative.
- Target absent → WaitingForEndpoint → zero worker processes.
- Reconnect → one fresh generation.

### Power lifecycle

- `WM_POWERBROADCAST` supplies suspend/resume facts.
- `PowerRevision` increments on resume.
- A pre-resume worker generation is never trusted after wake.
- Resume reuses the existing endpoint reconciliation path.

### Persistent evidence

Lifecycle logs are written under:

```text
%LOCALAPPDATA%\LEAudioRouter\logs\
```

Only low-frequency lifecycle transitions are persisted. Heartbeat, ring-fill warnings, overflow warnings, drift warnings, and per-second telemetry are deliberately excluded.

### Provisional positive-drift guard

The ring has 80 ms of physical storage, but its intended retained cushion remains approximately 10 ms.

The provisional guard regulates **post-render residual fill**:

```text
target residual       10 ms
gradual trim stops    11 ms
gradual trim starts   12 ms
hard recenter         20 ms
physical capacity     80 ms
```

It is explicitly temporary mitigation and must not be described as completed clock synchronization.

## Validation status

### Already tested before freezing this candidate

- connected startup → Running;
- Buds disconnect → zero workers / WaitingForEndpoint;
- no repeated worker PID churn while disconnected;
- reconnect → one new generation → Running;
- mode change → one generation replacement;
- invalid default output → TopologyBlocked;
- restoring valid default output → automatic recovery.

### Full daily-use validation now in progress

The following remain open evidence questions:

1. repeated Windows sleep/resume during ordinary use;
2. sleep while Buds are disconnected;
3. Buds disconnect/reconnect around resume;
4. multi-hour continuous audio;
5. multi-day accumulated lifecycle activity;
6. whether gradual frame slip is subjectively inaudible;
7. whether the 20 ms hard recenter is rare and operationally acceptable;
8. whether RuntimeDroppedAudioFrames stays meaningfully separated from intentional trim;
9. whether lifecycle logs stay compact and useful;
10. whether the historical long-run micro-crackle failure reappears.

## Release policy

This candidate must remain frozen while it is being tested.

If runtime code changes are required:

```text
round4/shell-bootstrap
    => fix / new implementation
    => new daily-test candidate if needed
```

Do not rewrite this candidate branch to hide a failed test.

Formal `V0.21` should only be created after the complete daily-use validation round is judged sufficient for the first public-facing baseline.
